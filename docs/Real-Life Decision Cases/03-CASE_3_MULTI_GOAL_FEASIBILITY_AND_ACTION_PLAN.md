# Case 3 — Multi-Goal Feasibility and Action Plan

> **Canonical lifecycle alignment — 2026-10-08**
> Multi-goal planning is a plan-level layer. Individual-goal Strategy Decision remains downstream of Goal Feasibility; Action Plan is downstream of investor adoption.

> **Core:** Financial State + Investor Intent/Goals → Goal Planning/Feasibility → Strategy Decision → Implementation Design → Stress/Resilience → Decision/Recommendation → Investor Decision → Accepted Plan → Action Plan → Execution.

> **Conditional:** Whole-Plan/Multi-Goal Impact is invoked only when the decision is plan-level.

> **Change loop:** Accepted Plan → Execution/What-If → Impact Analysis → Targeted Revalidation → Investor Decision → Updated Accepted Plan → Updated Action Plan.

> Goal Funding is owned by Goal Planner/Goal Feasibility; it is not a peer Strategy Builder strategy.

## 1. Real-Life Financial Case

A client has multiple financial goals that compete for the same available monthly surplus.

### Financial Situation

- Age: 38
- Monthly income: ₹3,00,000
- Monthly expenses: ₹1,60,000
- Existing EMI: ₹20,000
- Available monthly surplus: approximately ₹1,20,000
- Emergency reserve: adequate
- Debt: manageable based on the current financial state
- Risk capacity: adequate

### Goals

| Goal | Target | Horizon |
|---|---:|---:|
| Education | ₹50 lakh | 8 years |
| Retirement | ₹3 crore | 22 years |

Each goal may appear feasible when considered independently if the full available surplus is allocated to that goal. However, both goals cannot receive the full ₹1,20,000/month simultaneously.

Therefore, the real problem is not simply whether an individual goal is feasible.

The problem is whether the **complete set of goals is feasible together within the client's complete financial state**.

---

## 2. Question — Can Priority Alone Resolve the Problem?

No.

An earlier goal naturally requires greater attention than a much later goal. A human planner would normally think more about an education goal due in 8 years than retirement due in 22 years.

However, simply saying:

> "Education has higher priority, so allocate more to education."

does not solve the complete financial problem.

The system must determine:

- how much each goal needs;
- how much is actually available;
- what happens if one goal receives more;
- what happens to the other goals;
- whether alternative funding paths exist;
- whether the complete goal set can be made feasible;
- what actions are required to close any remaining gap.

**Priority is an input to the decision, not the complete decision mechanism.**

---

## 3. What the System Actually Needs to Do

The system must bring together:

**All Goals + Complete Financial State**

and evaluate them together.

This is the role of **Multi-Goal Planning / Goal Feasibility**.

The system should:

1. Understand the complete financial state.
2. Understand all active goals.
3. Calculate the funding requirement of each goal.
4. Calculate individual goal feasibility.
5. Calculate combined/multi-goal feasibility.
6. Identify where the available resources are insufficient.
7. Generate alternative paths to resolve the gaps.
8. Compare the consequences of those paths across all goals.
9. Determine a feasible overall path.
10. Convert the required changes into an **Action Plan**.

The output is therefore not simply:

> "Goal X is underfunded."

It should answer:

> "What needs to change for the overall financial plan to become feasible?"

---

## 4. Alternative Paths Must Be Considered

When there is a shortfall, the system should not immediately apply a single rule.

It should generate possible paths such as:

- increase monthly contribution;
- reduce or redirect an allocation from another goal;
- use an available lump sum;
- change the contribution pattern;
- increase contributions gradually;
- restructure an existing liability where appropriate;
- reduce unnecessary financial outflows;
- use another legitimate funding mechanism;
- change the goal timeline where acceptable;
- combine multiple actions.

Each alternative must be evaluated against the **whole financial picture**, not only the affected goal.

For example:

If Education requires ₹90,000/month but only ₹60,000 is currently available for it, the system should identify the ₹30,000 shortfall and determine possible actions.

One path could increase the education contribution.

Another could redirect part of the retirement contribution.

Another could use an available lump sum.

Another could change the funding pattern.

The system must then show the resulting effect on the other goals.

---

## 5. Action Plan Is the Actual Implementation Layer

The Action Plan should not be treated as merely:

- a report;
- a presentation layer;
- a reporting summary;
- a Strategy Builder output only.

**Action Plan is the actual implementation layer for the investor.**

It states what the investor needs to do to move from the current financial state toward the desired outcome.

Actions can originate from different parts of financial planning.

### Examples

| Financial finding | Possible Action |
|---|---|
| High-cost debt is reducing overall feasibility | Prepay/close the high-cost loan |
| Monthly goal contribution is insufficient | Increase monthly contribution by a specified amount |
| Available lump sum can close a funding gap | Deploy the required lump sum |
| Multiple goals compete for surplus | Reallocate contributions between goals |
| Loan restructuring improves goal feasibility | Restructure the loan and redirect released cash flow |
| Existing assets should be preserved | Use an appropriate financing path rather than liquidating assets |
| Strategy Builder selects a strategy | Execute the strategy-specific actions |
| Multiple actions are required | Sequence the actions and specify timing/amount |

Therefore, an Action Plan can contain both **planning-level actions** and **strategy-execution actions**.

---

## 6. Relationship Between Goal Planner and Strategy Builder

The two functions have different responsibilities.

### Goal Planner / Goal Feasibility

Answers:

> **"What needs to happen for the goals to become feasible?"**

It considers:

- complete financial state;
- all goals;
- funding requirements;
- competing goals;
- available surplus;
- assets and liabilities;
- liquidity;
- debt economics;
- alternative funding paths;
- opportunity cost;
- overall feasibility.

Its output can include the required actions to make the plan feasible.

### Strategy Builder

Answers:

> **"How should the feasible financial path be executed?"**

It determines the detailed implementation structure, such as:

**Strategy → Variant → Technique / Method → Solution → Action Plan → Execution**

For example, if education is feasible through a path that preserves existing investments and uses education financing, Strategy Builder may determine whether **Credit Utilisation** is an appropriate strategy and how it should be implemented.

## 7. Correct Overall Flow

The broader flow established by this case is:

**Complete Financial State + All Goals**

↓

**Multi-Goal Planning / Goal Feasibility**

↓

**Individual + Combined Feasibility**

↓

**Identify Funding Gaps / Financial Constraints**

↓

**Generate Alternative Paths**

↓

**Compare Impact Across All Goals**

↓

**Construct a Feasible Overall Path**

↓

**Action Plan**

↓

**Strategy Builder**

↓

**Strategy → Variant → Technique / Method → Solution**

↓

**Strategy Execution Actions**

The Action Plan therefore connects financial planning decisions to real-world execution.

---

## 8. What This Case Teaches

Case 3 is fundamentally different from the first two cases.

### Case 1

The key question was:

> **How should debt economics and opportunity cost affect goal feasibility?**

### Case 2

The key question was:

> **Once a goal is established as feasible, what funding mechanisms can be used and how should execution be structured?**

### Case 3

The key question is:

> **When multiple goals compete for the same financial resources, how can the complete financial plan be made feasible, and what actions must the investor take?**

This requires the system to move from **single-goal analysis** to **whole-financial-picture planning**.

---

## 9. Established Business Decisions

From this case, the following principles are established:

1. Multi-goal planning must evaluate all active goals together with the complete financial state.
2. Individual goal feasibility is not sufficient to establish overall plan feasibility.
3. Priority alone cannot resolve competing goals.
4. Earlier goal horizons can naturally receive greater attention, but this should not be the only decision mechanism.
5. The system must generate alternative paths when resources are insufficient.
6. Alternative paths must be evaluated for their impact on the other goals.
7. Goal Feasibility is not merely a calculation of whether a goal is funded.
8. Goal Planner / Multi-Goal Planning must identify what needs to change to make the overall plan feasible.
9. **Action Plan is the actual implementation layer.**
10. Action Plan can contain actions arising from debt, cash flow, goal funding, multi-goal allocation, and strategy execution.
11. Strategy Builder remains responsible for detailed strategy execution design.
12. Goal Planner determines the required financial path/actions; Strategy Builder determines the detailed strategy structure used to execute that path.
13. The exact mathematical optimization/allocation method is **not frozen by this case** and must be validated through further real-life cases.

---

## 10. Decision Boundary

The distinction established through the three cases is:

**Goal Planner / Goal Feasibility**

> Determine whether the desired outcomes can be achieved within the complete financial picture, identify alternative paths, and determine the actions required to make them feasible.

**Strategy Builder**

> Determine the detailed strategy and execution structure for carrying out the feasible financial path.

**Action Plan**

> Translate the required financial decisions and selected execution structure into the actual actions the investor needs to take.

This makes Action Plan a cross-cutting implementation layer rather than a reporting-only feature.
