# Decision Tree — Cross-Cutting Reverification & Gap Audit

## Purpose

This is the final cross-check after Steps 01–09. It does **not** freeze V1 or create new business rules.

It verifies whether the detailed audits captured the actual Strategy Builder decision/rule system and identifies remaining duplicate authorities, legacy identifiers, execution-order mismatches, and important dependencies.

## Audit Verdict

**Status: DOCUMENTED, BUT NOT READY FOR V1 FREEZE**

The 01–09 documents correctly cover the major Strategy Builder domains:

1. Strategy Applicability
2. Hard Constraints
3. 8 Eligibility Fits
4. Strategy Selection
5. 22 Variant Selection
6. Technique Selection
7. Architecture Composition
8. Stress / Resilience
9. Final Decision / Recommendation

The reverification did **not** find a missing major tenth decision stage.

The problem is instead that multiple generations of decision logic still coexist in the code.

### Critical findings

1. Legacy strategy decision rules are still present and referenced by executable code.
2. Legacy strategy identifiers remain in production code and tests.
3. Current runtime ordering does not yet match the proposed canonical ordering.
4. Architecture and technique work currently occur before final strategy selection.
5. Variant selection still occurs inside recommendation rather than as an independent authoritative stage.
6. Investor priorities need explicit ownership in the final decision contract.
7. The canonical rule registry is a metadata authority, but does not yet contain every important runtime business rule.
8. Several supporting rule modules exist, but they should remain dependencies/supporting layers rather than new decision stages.

Therefore the 01–09 documents should be retained. They should **not** yet be replaced by a frozen V1 rule document.

## 2. Legacy Strategy Decision Rules — CRITICAL

### Location

`backend/rules/strategy_decision.py`

The file contains older identifiers including:

- `strat-dynamic-accumulation`
- `strat-calibrated-growth`
- `strat-high-liquidity-flex`
- `strat-cap-preservation`

These do not match the current canonical five-strategy library.

### Why this matters

This is not merely old documentation. The current strategy decision/scoring path still consumes logic associated with this older rule surface.

Therefore this is a genuine **canonicalization conflict**.

### Before V1

- Determine which old rules are obsolete.
- Map any still-required behavior to the current five canonical strategies.
- Remove or replace obsolete IDs.
- Update affected tests.
- Ensure no executable decision path references obsolete IDs.

## 5. Current Runtime Order vs Proposed Canonical Order

### Current implementation

The StrategyEngine effectively performs:

**Applicability → Scenario Generation → Architecture Composition → Technique Execution → Decision → Ranking → Recommendation**

Variant selection is subsequently performed inside recommendation.

### Proposed canonical design

**Goal → Goal Classification → Hard Constraint Gate → Strategy Applicability → 8-Fit Eligibility → Strategy Selection → Variant Selection → Technique Selection → Architecture Composition → Stress / Resilience → Final Decision → Recommendation**

These are materially different.

Therefore the current implementation must **not** be described as already implementing the proposed canonical decision tree.

This is a design target, not a frozen runtime contract.

---

## 6. Architecture Is Currently Upstream of Final Strategy Selection

Current StrategyEngine flow:

1. determine applicable strategies;
2. generate scenarios;
3. compose architectures;
4. execute techniques;
5. evaluate the decision.

The target model treats architecture as downstream:

**Strategy → Variant → Technique → Architecture**

Current behavior is closer to:

**Strategy candidates → Architecture candidates → Technique execution → Strategy decision**

This creates a potential circular dependency.

### V1 decision required

Explicitly decide:

> Does architecture influence strategy selection, or is architecture purely downstream of strategy/variant/technique selection?

This cannot remain implicit.

---

## 7. Variant Selection Is Not Yet an Independent Decision Stage

Variant definitions are canonical in:

`backend/library/strategies/variants.py`

Selection logic remains in:

`backend/engines/strategy/variant_selector.py`

and is invoked from:

`backend/engines/strategy/recommendation.py`

Therefore the current runtime does not yet implement three independent authoritative stages:

**Strategy Selection → Variant Selection → Technique Selection**

V1 requires one canonical owner for variant selection and deterministic precedence rules for all 22 variants.

---

## 8. Investor Priorities Need Explicit Decision Ownership

The StrategyEngine requires investor priorities and ranking consumes them.

However, the authoritative strategy decision layer does not currently establish investor priorities as a clearly independent selection gate/factor in the target contract.

Before V1, explicitly decide whether investor priorities are:

- a hard decision constraint;
- an eligibility input;
- a ranking factor;
- a recommendation preference;
- or a combination with explicit precedence.

The same priority information must not silently influence multiple layers.

## 9. Canonical Rule Registry Is Not Yet Complete

### Location

`backend/rules/canonical.py`

The registry is a useful metadata authority for:

- rule ID;
- scope;
- role;
- source module;
- description;
- version.

It already covers many goal, MoneyWheel, eligibility, multi-goal and protection rules.

However, important runtime behavior still lives outside it, including examples such as:

- emergency-reserve critical behavior;
- debt-burden critical behavior;
- attention warnings;
- strategy applicability conditions;
- variant-selection conditions;
- technique-selection conditions;
- supporting-strategy composition conditions;
- stress/resilience policy.

Therefore:

> The current canonical registry is a **metadata registry**, not yet a complete canonical business-rule registry.

This distinction must remain explicit until V1.

- safety;
- liquidity;
- growth;
- flexibility;
- funding gap;
- required contribution;
- return assumptions;

## 12. Probability of Success Must Not Become an Unverified Decision Rule

The comparison layer can expose `probability_of_success`, but the current code explicitly supports cases where it is unavailable/not estimated.

Therefore:

> Probability-of-success should only influence canonical strategy selection after a real, validated probability model is defined.

Until then it is evidence when genuinely available, not an implicit selection rule.

- Goal Positive Target

## 14. Ranking Is Not the Authoritative Decision

The ranking layer consumes the authoritative DecisionResult.

Therefore the intended authority is:

**Decision → Ranking**

not:

**Ranking → Decision**

The safety/liquidity/growth/flexibility composite should remain descriptive until its role is explicitly frozen as a decision factor.

## 19. Final Audit Conclusion

The 01–09 documents did **not** miss another major Strategy Builder decision domain.

The real issue is:

> **Multiple generations of the same decision logic coexist in the system.**

The risk is therefore:

**old rule → compatibility rule → current engine rule → new canonical rule**

coexisting for the same business concept.

That is the System Drift we are trying to remove.

The correct next phase is:

**Cross-Cutting Reverification → Rule Ownership Resolution → Real-Life Validation → Canonical V1 Freeze → Refactor**

Not immediate code refactoring.

## 20. Coding-Agent Full-Document Verification — Confirmed Findings

A full verification of the Decision Tree documents against the current backend confirmed the core audit, with these important clarifications:

1. **Hard constraints:** the `discretionary-cannot-preempt-essential` function/rule is declared but is not currently invoked by the financial constraint evaluator. It must not be described as fully enforced until wiring is verified.
2. **Strategy scoring:** legacy strategy IDs remain active in `rules/strategy_decision.py`; Horizon Fit therefore does not apply its intended optimal branches to the current canonical strategy IDs.
3. **InvestorPriorities:** `evaluate_decision()` accepts priorities but does not use them in its calculation. Current mathematical influence is in ranking, not strategy selection.
4. **Eligibility:** `decision.py` currently invokes both the eight-fit evaluator and a separate eligibility gate. These overlapping checks need one clearly defined business owner.
5. **Variants:** all 22 variants are defined, but Goal Funding's direct fallback selector reaches only 3 of its 6 variants unless the scenario is already bound to another variant.
6. **Architecture order:** architecture composition and technique execution precede the authoritative decision call in the current runtime. The documented canonical sequence is therefore a target, not current runtime truth.
7. **Hard-constraint semantics:** critical emergency reserve/DTI conditions can produce priority overrides for affected discretionary goals rather than universally stopping the Strategy Builder.

**Conclusion:** the existing cross-cutting audit is directionally correct, but these details are now explicitly part of the verified current state. No implementation change is implied by this documentation update.
