# Strategy Builder Rule Ownership — KEEP / MERGE / REPLACE / REMOVE / NEW Audit

## Purpose

This is the **Rule Ownership Audit** for the Strategy Builder decision tree only.

It is an audit of the current repository code. It does **not** refactor or change runtime behaviour.

The purpose is to decide, before implementation:

- which rule source remains authoritative;
- which rules are duplicates and should be merged;
- which old rules must be replaced;
- which compatibility/legacy rules should be removed;
- which missing rules must be created.

## Canonical decision flow under audit

Goal → Hard Constraint Gate → Strategy Applicability → 8-Fit Eligibility → Strategy Selection → Variant Selection → Technique Selection → Architecture Composition → Stress/Resilience → Final Decision → Recommendation

The audit treats this as the target decision flow, not as proof that the current runtime already follows it exactly.

## 2. KEEP

### A. Canonical strategy library

**Owner:** `backend/library/strategies/canonical.py`

Keep the five current canonical strategies:

1. Goal Funding — `strat-goal-funding`
2. Progressive De-risking — `strat-progressive-de-risking`
3. Capital Preservation — `strat-capital-preservation`
4. Debt Reduction — `strat-debt-reduction`
5. Credit Utilisation — `strat-credit-utilisation`

This is the canonical Strategy Library. No old strategy should be reintroduced merely to satisfy an old scoring rule.

### B. Canonical variants

**Owner:** `backend/library/strategies/variants.py`

Keep the current **22 active variants**.

Variants are children of a strategy. They must not become separate strategies.

### C. Canonical techniques

**Owner:** `backend/library/strategies/techniques_canonical.py`

Keep the 10 registered techniques.

Technique definitions remain reusable methods. They are not strategy definitions.

### D. Applicability

**Owner:** `backend/engines/rules/engine.py` / `StrategyRuleEngine`

Keep the current applicability concept:

Goal type + goal characteristics → applicable strategy candidates.

Component activation must not silently remove an otherwise applicable strategy; it belongs to later architecture composition.

### E. Eligibility vocabulary

**Owner:** `backend/rules/eligibility.py`

Keep:

- PASS
- CONDITIONAL
- FAIL

and the eight canonical fits:

1. cashflow_fit
2. liquidity_fit
3. debt_fit
4. asset_resource_fit
5. risk_capacity_fit
6. goal_constraint_fit
7. multi_goal_conflict_fit
8. implementation_fit

### F. ConstraintSet

**Owner:** centralized constraints layer / `ConstraintAggregator`

Keep the centralized ConstraintSet as the input to the Strategy Builder.

Hard constraints must remain different from explanatory diagnostics.

## 3. MERGE

### A. Eligibility rule ownership

Current split:

- `backend/rules/eligibility.py` defines the canonical vocabulary/statuses.
- `backend/engines/strategy/eligibility.py` contains the actual fit calculations.

**Decision: MERGE ownership, not necessarily files.**

Recommended final ownership:

- `rules/eligibility.py` = canonical definitions, IDs, status vocabulary and metadata.
- `engines/strategy/eligibility.py` = one executable implementation of those rules.

There must be no second implementation of the same eight fits elsewhere.

### B. Strategy selection scoring

Current split:

- `backend/rules/strategy_decision.py` contains scoring constants/functions.
- `backend/engines/strategy/decision.py` orchestrates eligibility, scoring, candidate comparison and final selection.

**Decision: MERGE into one canonical decision policy.**

The engine may remain the execution/orchestration layer, but the business meaning of the score must have one owner.

The current stale IDs in `rules/strategy_decision.py` make the present split unsafe to freeze.

### C. Canonical rule registry

**Decision: EXTEND/MERGE ownership.**

`backend/rules/canonical.py` already registers eligibility rules and other policy rules. It should become the authoritative catalog for Strategy Builder rule identity/role.

It should not duplicate executable calculations. It should identify the canonical rule and its owner.

## 4. REPLACE

### A. Old strategy scoring vocabulary

The following IDs still appear in `backend/rules/strategy_decision.py`:

- `strat-dynamic-accumulation`
- `strat-calibrated-growth`
- `strat-high-liquidity-flex`
- `strat-cap-preservation`

These do not match the five canonical strategies.

**Decision: REPLACE with canonical strategy IDs.**

This is not a cosmetic rename. The underlying horizon/funding scoring meaning must be mapped to the five current responsibilities.

The correct mapping must be decided explicitly before code replacement; it should not be guessed from names.

### B. Current stress/what-if layer

`backend/engines/strategy/scenario.py` currently provides baseline and what-if scenarios.

**Decision: REPLACE/EXTEND for the stress stage.**

What-if scenarios are useful exploration, but they are not yet a formal resilience decision gate.

The final system needs a clear rule answering:

> Does the selected strategy remain acceptable under defined adverse conditions?

---

## 5. REMOVE

### A. Legacy strategy IDs after migration

Remove production use of:

- `strat-dynamic-accumulation`
- `strat-calibrated-growth`
- `strat-high-liquidity-flex`

Remove `strat-cap-preservation` after all compatibility/test usage is migrated to:

`strat-capital-preservation`

### B. Legacy alias

Current registry contains:

`strat-cap-preservation → strat-capital-preservation`

**Decision: temporary compatibility only.**

It should be removed once all callers/tests/data are migrated.

Do not allow the alias to become part of the canonical Strategy vocabulary.

### C. Duplicate decision authority

Any future duplicate implementation of:

- applicability;
- the eight fits;
- strategy selection scoring;
- variant selection;

must not be retained merely for backward compatibility.

There should be one business owner for each.

---

## 6. NEW

The audit identifies the following missing/frozen decisions.

### A. Canonical strategy-selection policy

A single explicit policy must define:

- which inputs can eliminate a strategy;
- which inputs can score a strategy;
- how PASS vs CONDITIONAL is handled;
- how investor priorities affect the score;
- how ties are resolved;
- what happens when no strategy passes.

### B. Canonical mapping from old scoring concepts to five strategies

The old scoring functions use strategy IDs that no longer exist.

Before refactoring, create an explicit mapping for:

- horizon fit;
- funding fit;
- goal fit;
- feasibility;
- component fit;
- technique execution.

### C. Formal stress/resilience gate

Define:

- stress scenarios;
- required inputs;
- pass/fail/conditional thresholds;
- whether failure triggers re-selection;
- whether resilience changes the strategy, variant, technique or only implementation.

### D. Explicit decision ownership for InvestorPriorities

`InvestorPriorities` currently contains:

- safety
- liquidity
- growth
- flexibility

The final V1 policy must explicitly state whether these:

1. select among already-eligible strategies;
2. only rank eligible strategies;
3. influence both selection and ranking.

Only one interpretation should remain.

## 8. Important finding: current runtime is not yet the target flow

The repository currently executes architecture composition and technique execution before the authoritative `evaluate_decision()` call.

That means the target sequence:

**Strategy → Variant → Technique → Architecture → Stress → Final Decision**

is **not yet the exact runtime sequence**.

This must be resolved in the implementation phase. Do not call the current runtime V1 until this is deliberately fixed.

---

## 9. What we should NOT do yet

Do **not** immediately delete `backend/rules/strategy_decision.py`.

Do **not** immediately rename the old strategy IDs.

Do **not** immediately reorder the StrategyEngine.

Do **not** add a stress model based on assumptions.

First freeze the business mapping.

Otherwise we risk replacing one form of system drift with another.

---

## 10. Required next step

The next task is a **real-life decision validation**.

We should create representative financial cases and ask:

> For this investor and this goal, which strategy should the system choose, and why?

At minimum test:

1. Long-horizon goal with healthy surplus.
2. Short-horizon goal with large funding gap.
3. Goal with surplus but insufficient liquidity.
4. Goal with significant debt burden.
5. Goal where investor risk capacity is low.
6. Goal competing with a higher-priority goal.
7. Goal where multiple strategies pass.
8. Goal where all strategies fail.
9. Goal requiring de-risking.
10. Goal where resilience testing should cause re-selection.

For every case compare:

**Expected business decision → current code decision → difference → rule causing difference.**

Only after this should the canonical V1 decision policy be frozen.

---

## Final audit conclusion

The repository is **not suffering from a lack of Strategy Builder components**.

The main problem is that **multiple generations of decision rules coexist**.

The most important cleanup is:

**one canonical strategy vocabulary + one applicability owner + one 8-fit owner + one strategy-selection policy + one variant selector + one technique owner + one architecture owner + one stress/resilience gate + one final decision owner.**

Until that ownership is frozen, further refactoring would be premature.

## 11. Coding-Agent Verification Clarifications

The ownership audit was verified against the full current Decision Tree implementation. The following points are now explicitly confirmed:

### 11.1 Hard constraints are not all universal blockers

Critical emergency-reserve and DTI conditions can produce a priority override/demotion for affected discretionary goals. Therefore **KEEP Hard Constraints** does not mean “every hard constraint universally blocks every goal.” The eventual V1 policy must define block vs demote vs condition vs warning.

### 11.2 InvestorPriorities is not currently a strategy-selection input

`evaluate_decision()` accepts `InvestorPriorities`, but the current function body does not use it to calculate the winning strategy. Ranking currently uses the priorities. Therefore the earlier wording “input to decision-making” must remain **unfrozen** until business policy decides whether priorities select, rank, or both.

### 11.3 Eligibility has overlapping checks

The decision path currently runs both `evaluate_eligibility_fits()` and the separate `evaluate_eligibility()` gate. This is a real competing/overlapping authority and must be resolved before V1.

### 11.4 Goal Funding variant reachability is incomplete

All 6 Goal Funding variants exist, but direct fallback selection reaches only `existing_assets`, `lumpsum`, and `step_up_sip` when no scenario is pre-bound. `sip`, `lumpsum_plus_sip`, and `lumpsum_plus_step_up_sip` are not independently selected by that fallback path.

### 11.5 Architecture timing is a current-runtime defect/decision point

The current runtime composes architectures and executes techniques before the authoritative strategy decision. Therefore “architecture downstream of strategy selection” is a **target decision**, not an already-implemented fact.

### 11.6 Rule registry is metadata, not execution authority

`backend/rules/canonical.py` provides rule identity/metadata; it does not currently contain all executable Strategy Builder business logic. It should not be treated as if it already were the complete canonical execution registry.

These clarifications do not change the KEEP/MERGE/REPLACE/REMOVE/NEW decisions themselves. They make the current-state evidence explicit before real-life validation.
